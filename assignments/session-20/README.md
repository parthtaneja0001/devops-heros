## 1. Monitoring vs. Observability

| Concept | Primary Focus | Key Question Answered | Paradigm |
| :--- | :--- | :--- | :--- |
| **Monitoring** | Tracks known failure modes, metrics, and thresholds. | *"Is the system working right now?"* | Symptom-focused (Black box) |
| **Observability** | Infers internal state based on external telemetry data. | *"Why is the system behaving this way?"* | Cause-focused (White box) |

## 2. The Three Pillars of Observability

Observability rests upon three distinct types of telemetry data:

1. **Metrics:** Aggregated numerical time-series data over time (e.g. CPU utilization, request throughput, error rates).
2. **Logs:** Immutable, timestamped text or structured JSON records documenting individual events.
3. **Traces:** End-to-end request paths across distributed microservice architectures, tagged with unique Trace and Span IDs.

## 3. Prometheus — Time-Series Monitoring

**Prometheus** is an open-source time-series database and monitoring tool that uses a **pull-based** model to scrape HTTP `/metrics` endpoints exposed by target services.

- **PromQL (Prometheus Query Language):** Powerful query language used to calculate rates, aggregations, and quantiles (e.g., `rate(http_requests_total[5m])`).
- **Alertmanager:** Handles alerts generated by Prometheus rules (deduplication, grouping, routing to Slack/PagerDuty).

## 5. Introduction to GitOps

**GitOps** is an operational framework that takes DevOps best practices used for application code (version control, code review, CI/CD) and applies them to infrastructure automation.

### Core GitOps Principles

1. **Declarative Specification:** The entire system state is described declaratively in Git.
2. **Git as Single Source of Truth:** Desired system state is version-controlled in a Git repository.
3. **Automated State Pulling:** Software agents in the cluster continuously compare desired state (Git) against actual state (Cluster).
4. **Drift Correction & Self-Healing:** Automated reconciliation ensures any unauthorized manual changes in the cluster are overwritten by Git.

| Pull Model (GitOps / Argo CD) | Push Model (Traditional CI/CD) |
| :--- | :--- |
| Agent inside cluster pulls state from Git | External CI runner pushes changes to cluster |
| No cluster credentials exposed outside | Cluster credentials stored in CI/CD secrets |
| Automatic drift detection & self-healing | No continuous state reconciliation |

## 7. Declarative GitOps with Argo CD

**Argo CD** is a declarative, GitOps continuous delivery tool for Kubernetes. It runs as a controller inside the cluster, monitoring Git repositories and syncing resources to target namespaces.

- **`Application` CRD:** Defines the source Git repository/path and target Kubernetes cluster/namespace.
- **Automated Sync Policy:**
  - **Prune:** Automatically deletes cluster resources removed from Git.
  - **Self-Heal:** Automatically overrides manual `kubectl` changes to match Git.
  - **CreateNamespace:** Automatically creates missing target namespaces.

## Summary & Key Takeaways

- **Monitoring vs. Observability:** Monitoring notifies you when something breaks; **observability** provides the telemetry needed to understand why it broke.
- **The Telemetry Triad:** **Metrics** give numerical trends, **Logs** detail specific events, and **Traces** follow request paths across services.
- **Prometheus & Grafana:** Prometheus scrapes metrics using PromQL, while Grafana visualizes those metrics on dashboards.
- **GitOps Continuous Delivery:** **Git** serves as the single source of truth, and **Argo CD** continuously reconciles live cluster state with Git, preventing configuration drift and simplifying deployments.
